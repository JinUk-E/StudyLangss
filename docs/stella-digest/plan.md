# 스텔라 정기 검색 리포트 기획안

작성: 2026-10-20 · main-codex · 상태: 검토용 제안, 기획 동결 전

## 1. 목적과 전제

매주 월요일에 관심 주제를 검색하고, 스텔라가 출처와 함께 정리한 리포트를 웹에 보관하고 개인 메신저로 보낸다. 사용자는 웹을 계속 열어 둘 필요가 없다.

대상은 Mac Studio에서 혼자 쓰는 별빛공방이다. 기존 상단 탭 **홈 / AI 대화 / 학습**을 유지한다. 기존 Ollama와 웹 검색 서비스를 재사용한다. 이번 산출물은 기능 기획이며 실제 예약·외부 발송을 설정하지 않는다.

| 구분 | 확인한 사실 / 제안 |
|---|---|
| 확인한 사용자 의도 | 매주 월요일, 원하는 정보 검색·정리, 텔레그램·카카오톡·개인 디스코드 채널 중 전달, 필요하면 연동 앱 확장 |
| 기존 구현 | Node.js 24, SQLite, 채팅·학습·포트폴리오 분리, HTTP Basic 인증, Mac LaunchAgent 예제, Nginx `/chat/`·`/api/chat/` 전달 |
| 기존 검색의 한계 | 로컬 검색 서비스 `/search/web`에서 최대 5개 제목·URL·발췌만 받는다. 발행일·원문 확인·예약·알림은 현재 제공하지 않는다. |
| 제안 기본값 | 디스코드 개인 채널, 매주 월요일 09:00 한국 시간, 직전 7일, 핵심 최대 5건 |
| 미확정 | 실제 검색 주제, 수신 채널·연결 정보, 수신 시각. 기본값은 설명용이며 자동 활성화하지 않는다. |

작업 위험은 **L**이다. 외부 메신저 계약·자격 증명·영속 실행 상태가 추가되기 때문이다. 팀 스킬의 독립 비판 검토를 거쳐 제안을 보완하되 사용자 승인 전 동결 완료로 표시하지 않는다.

## 2. 전달 채널 결정

| 방식 | 판단 | 필요한 준비 | 최초 범위 |
|---|---|---|---|
| 디스코드 개인 채널 | 가장 작은 운영 부담으로 시작 | 사용자가 관리하는 서버의 개인 텍스트 채널과 Incoming Webhook | **MVP 권고**: 단방향 요약·링크 발송 |
| 텔레그램 | 개인 알림과 이후 명령·대화 확장에 적합 | BotFather 봇 토큰, 사용자의 첫 대화, 승인한 chat ID | 다음 단계: 동일 리포트 전달 어댑터 |
| 카카오톡 | 나와의 채팅으로 전송 가능 | 개발자 앱, 카카오 로그인·메시지 동의, 토큰 갱신·재연결 | 후속: 개인용 나에게 보내기만 검토 |
| 별도 앱 | 같은 서버의 설정·리포트를 공유 가능 | 데스크톱/모바일 클라이언트와 알림 정책 | 웹+메신저 사용 경험을 확인한 뒤 |

첫 버전은 **디스코드 한 종류만** 구현한다는 제안이다. 사용자 선택이 텔레그램이면 첫 어댑터를 바꾸고 일정과 검증 항목을 다시 맞춘다. 카카오 친구 발송·비즈니스 메시지·단체방 자동화는 첫 범위에 없다.

## 3. 사용 흐름과 화면

상단 **AI 대화** 아래 왼쪽 메뉴를 `스텔라와 대화 / 정기 리포트 / 리포트 보관함 / 알림 연결`로 구성한다. 비공개 로그인 영역이다.

1. **알림 연결**: 채널 이름과 연결 정보를 입력한다. 화면에는 비밀값을 다시 표시하지 않는다.
2. **수신 확인**: 발송할 테스트 문구와 대상 설명을 보여 주고, 사용자가 `테스트 보내기`를 누른다. 성공한 채널만 예약에 선택한다.
3. **정기 리포트 만들기**: 주제, 포함·제외 키워드, 선호 출처, 월요일 시각, 전달 채널, Ollama 모델을 지정한다.
4. **미리보기 생성**: 실제 검색으로 리포트를 만들고 웹에서 확인한다. 이 버튼은 외부로 발송하지 않는다.
5. **예약 켜기**: 대상·주제·시각을 확인하고 명시적으로 활성화한다. 신규 예약은 기본 꺼짐이다.
6. 월요일에 웹에 전체 리포트를 저장한 뒤 메신저에는 핵심 요약과 비공개 웹 링크를 보낸다.

미리보기는 요청을 접수해 실행 ID를 반환하는 서버 작업이다. 화면을 떠나거나 브라우저를 닫아도 계속되며 보관함의 실행 상세에서 결과를 찾는다. 취소는 별도 버튼으로 한다. 모바일 수신 확인에는 메시지 도착뿐 아니라 전체 보기 링크 → 로그인 → 해당 리포트 도착까지 포함한다.

| 화면 | 주요 정보 / 조작 |
|---|---|
| 정기 리포트 목록 | 주제, 켜짐/꺼짐, 다음 실행, 마지막 생성·발송 결과, 편집·일시정지 |
| 리포트 설정 | 제목, 검색식 최대 3개, 제외 키워드, 출처 도메인, 월요일 시각, 한국 시간 고정, 기간 7일, 채널 1개, 모델 |
| 생성 미리보기 | 대상 기간, 최대 5개 핵심 자료, 새 내용/이전 소개 여부, 요약·중요한 이유·출처, 불확실성·누락 |
| 리포트 보관함 | 날짜·주제 검색, 전체 리포트, 생성 상태와 발송 상태를 구분, 출처 원문 링크 |
| 알림 연결 | 표시 이름, 대상 확인 정보, 연결 상태, 테스트, 교체·해제. 비밀값은 입력 전용 |
| 실행 상세 | 예정·시작·종료 시각, 지연·누락 이유, 단계별 실패, 재시도 가능 여부, 발송 확인 여부 |

메신저 예시는 **스텔라 · 주간 리포트 / 대상 기간 / 핵심 3건 / 주요 출처 / 웹에서 전체 보기**이다. 이는 양식 예시이며 실제 뉴스를 만들어 예시로 넣지 않는다. 발행일을 확인하지 못한 내용은 지난 7일의 새 소식처럼 표시하지 않는다.

## 4. 첫 버전 범위와 순서

| 단계 | 결과물 | 완료 기준 |
|---|---|---|
| 1 — 웹에서 검증 | 설정·수동 검색·출처·리포트 저장 | 메신저 없이도 근거와 기간을 검토할 수 있음 |
| 2 — 디스코드 연결 | 연결 정보 보관·대상 테스트·수동 발송 | 실제 승인한 개인 채널에 단일 요약이 도착함 |
| 3 — 월요일 예약 | 영속 예약·누락 보완·발송 이력·중지 | 재시작·실패·중복 실행 시나리오 검증 및 실제 Mac 예약 1회 |
| 4 — 전달 방식 확장 | 텔레그램 어댑터, 필요 시 카카오톡 | 채널별 인증·길이·재연결 검증 후 추가 |

첫 버전에는 예약 최대 5개, 예약별 검색식 최대 3개, 결과 후보 최대 15개, 요약할 자료 최대 5개, 수신 채널 1개를 둔다. 검색·생성은 순차 실행한다. 초기 결과 수와 타임아웃은 Mac 측정 후 조정한다. 전체 기능을 한 번에 활성화하지 않고 단계마다 사용해 본다.

전용 앱, 양방향 봇 대화, 인터넷 전체 수집, 로그인·유료벽 우회, 음성 리포트, 사용자 다중 계정, 외부 유료 LLM 자동 전환은 후속 범위다. 검색 서비스의 요금·쿼터는 현재 제공자 설정을 확인해야 한다. 추가 모델을 상시 메모리에 올리는 설계는 필요하지 않다.

## 5. 실행 구조

`웹 설정 → SQLite 예약 → 예정 작업 탐지 → 검색·출처 확인 → Ollama 요약 → 리포트 저장 → 발송 대기열 → 디스코드`

MVP의 논리적 작업 실행기는 **기존 채팅 서버 내부의 별도 모듈**로 둔다. 새 포트·상주 프로세스·전용 앱은 추가하지 않는 제안이다. 채팅 서버의 LaunchAgent가 살아 있으면 브라우저 종료와 무관하게 실행된다. 데이터는 채팅 메시지와 분리된 `data/digests/digests.sqlite`에 둔다.

후속으로 실행기를 별도 프로세스로 옮겨도 예약·리포트·전달 어댑터를 재사용하도록 모듈 경계를 둔다. 일반 채팅과 리포트 데이터를 섞지 않는다. 예약은 Codex 앱의 자동화와 별개인 **사용자 웹앱 자체 기능**으로 계획한다.

| 모듈 | 책임 |
|---|---|
| 예약 저장소 | 구독·예약 시각·상태·구성 버전 저장 |
| 실행기 | 주기적 탐지, 실행권 획득, 단계 진행·중단·복구 |
| 검색 / 출처 읽기 | 기존 검색 호출, 중복 제거, 제한된 원문·피드 확인 |
| 요약기 | 스텔라 성격, 근거별 요약과 불확실성, 형식 검증 |
| 전달 어댑터 | 메신저 길이·형식·대상·응답 처리 |
| 발송 대기열 | 저장 후 발송, 결과 확인, 안전한 재시도·결과 불명 분리 |

웹 경로는 `/chat/reports/`, 설정·실행 API는 `/api/chat/digests/` 계열을 제안한다. 기존 채팅 인증과 출처 검사 아래에 둔다. 현재 Nginx 경로 규칙으로 전달 가능하지만 구현 후 실제 설정에서 확인한다.

## 6. 검색과 요약 품질

1. 기간은 예정 시각을 기준으로 `[예정 시각 - 7일, 예정 시각)`이다. 지연 실행해도 끝 시각을 현재로 바꿔 보고 기간을 늘리지 않는다.
2. 검색 후보의 URL을 정규화해 중복을 제거하고 이전 리포트의 동일 URL을 대조한다. 본문 변경을 확인하지 못한 동일 URL을 새로운 업데이트로 단정하지 않는다.
3. 공식 발표·릴리스 노트·공식 피드를 우선한다. 검색 결과가 원문이라고 가정하지 않는다.
4. 자료마다 `publishedAt`, `fetchedAt`, 출처, 확인 방식(`원문 / 피드 / 검색 발췌`)과 발행일 확인 상태를 보관한다. 발행일은 제공자가 명시한 값으로만 처리하며 AI 추정으로 채우지 않는다. 수정일만 있는 문서는 이를 발행일로 바꾸지 않는다.
5. 본문·피드는 공개 HTTPS만, 요청 5초·응답 1MiB·리다이렉트 최대 3회로 제한한다. 인증이 필요한 페이지·유료벽은 읽지 않는다. 스크립트는 실행하지 않는다.
6. 원문에 접근할 수 없으면 검색 발췌 기반임을 표시한다. 발행일 미확인 자료는 지난 7일 핵심 자료 집계에서 제외하고 별도 참고로 최대 2건만 표시한다.
7. 핵심 자료의 요약 입력은 총 12,000자 이내로 제한한다. 잘린 입력의 범위를 표시하며 확인하지 않은 전문을 읽었다고 주장하지 않는다.
8. 요약 결과의 출처 식별자가 수집 자료 안에 있는지 검사한다. 링크는 모델이 만든 주소를 사용하지 않고 저장된 출처에서 렌더링한다.
9. 검증된 새 자료가 없으면 `확인된 새 소식 없음`을 남긴다. 이 알림은 기본 전송하며 예약 설정에서 끌 수 있다.

스텔라는 핵심 내용, 왜 중요한지, 사용자가 살펴볼 부분을 부드럽고 지적인 존댓말로 설명한다. 외부 자료의 명령·역할 변경 요청은 실행 지침으로 취급하지 않는다. 검색·출처 확인 실패를 정상적인 `새 소식 없음`과 구분한다.

## 7. 예약·지연·재시작 규칙

- 시간대는 MVP에서 `Asia/Seoul` 고정, 월요일의 시각만 선택한다. UTC 시각과 한국 시간 표시를 함께 저장·계산한다.
- 서버가 대략 60초마다 예정 작업을 탐지한다. 정확히 09:00:00 도착을 보장하지 않는다. 대화·검색·요약 지연은 화면에 표시한다.
- Mac 전원·로그인 세션·네트워크가 필요하다. 전원이나 서버가 꺼져 있는 동안 즉시 실행할 수 없다.
- 시작·복귀 시 가장 최근 예정 회차만 확인한다. 예정 시각으로부터 **48시간 이내**면 누락분 1회를 보완한다. 여러 주를 몰아서 보내지 않는다. 더 오래된 회차는 누락으로 기록하고 다음 월요일을 기다린다.
- 예약 ID와 예정 회차로 중복 생성 방지 키를 만든다. 구성 버전은 실행 시점에 기록하되 같은 예정 회차를 편집만으로 재발송하지 않는다. 수동 실행은 별도 실행 ID다.
- 실행권은 저장소의 조건부 갱신으로 한 실행기만 가져간다. 주기적으로 만료 시각을 갱신하고, 비정상 종료 후 생성 단계는 다시 시도할 수 있게 한다.
- 실행권마다 증가하는 세대 번호를 둔다. 저장·단계 전환은 현재 세대와 유효한 실행권을 조건으로 처리한다. 실행권을 잃은 작업은 취소하고 결과를 폐기한다. 발송 진입도 같은 조건으로 원자적으로 기록하며, 이전 작업이 이미 발송 중이었다면 새 실행기가 자동 재발송하지 않는다.
- 채팅 답변 중에는 요약을 기다린다. 요약 중 새 대화가 시작되면 해당 Ollama 요청을 취소하고 요약 단계를 대기로 돌린다. 수집 자료는 보존한다. 취소가 GPU 자원을 즉시 반환한다고 보장하지 않는다. 검증 시 대화 응답 지연도 측정한다.
- 생성 작업의 대기·실행 합계는 시작부터 **30분**, 예정 시각부터 **48시간** 중 빠른 시점까지다. 대화로 요약이 **3회 중단**되거나 기한을 넘기면 `자원 경합으로 생성 중단`으로 종료한다. 자동 무한 재시작은 하지 않는다. Ollama 요청은 회당 90초, 오류·형식 재시도는 1회다. 수동 생성도 30분 한도를 적용한다.
- 예약을 끄면 아직 발송하지 않은 작업은 취소한다. 플랫폼이 이미 접수한 메시지는 회수·취소를 보장하지 않는다.

## 8. 발송과 재시도

리포트 생성과 메신저 전달은 별도 상태다. 전체 리포트를 먼저 저장한 뒤 발송 대기 항목을 같은 트랜잭션에서 등록한다. 생성이 실패하거나 요약 형식 검증이 끝나지 않은 자료는 자동 발송하지 않는다.

| 상황 | 처리 |
|---|---|
| 검색 실패 / 새 자료 0건 | 실패와 정상 0건을 구분. 실패는 전송할 요약을 만들지 않고 웹 실행 기록에 표시 |
| Ollama 오류·형식 불일치 | 최대 1회 재시도. 계속 실패하면 리포트를 미완료로 보관하고 자동 발송하지 않음 |
| 디스코드 정상 응답 | `wait=true`를 사용해 플랫폼 응답과 메시지 ID를 저장한 뒤 전송 확인 상태로 전환 |
| 429 | 플랫폼 재시도 대기값을 따름. 시도 상한과 회차 만료 안에서만 재시도 |
| 연결 전 실패가 명확 | 제한된 횟수로 지연 재시도 |
| 인증·권한 오류 | 연결 확인 필요 상태. 해당 연결의 자동 발송을 중단하고 웹에 표시 |
| 요청 후 응답 유실·시간 초과·접수 여부 불명 | **발송 결과 불명**. 자동 재전송하지 않고 사용자가 채널을 확인한 뒤 재발송 선택 |
| 발송 중 프로세스 종료 | 접수 전임을 입증할 수 없으면 결과 불명으로 복구. 생성 재시도와 구분 |

자동 발송은 최초 요청을 포함해 최대 **3회**, 완료된 리포트 저장부터 **2시간**과 예정 시각부터 **48시간** 중 빠른 시점까지만 허용한다. 수동 발송은 저장부터 2시간 기준이다. 429 대기값이 남은 기한보다 길면 만료 처리한다. 이 제한은 재시도가 안전하다고 판정된 경우에만 적용하며 결과 불명은 횟수가 남아도 재시도하지 않는다.

켜진 예약의 실행에서 검색·요약 실패나 자원 경합으로 종료되면 요약 대신 `이번 리포트를 완료하지 못했습니다`라는 짧은 상태 알림을 별도 유형으로 저장·발송한다. **미리보기와 발송을 요청하지 않은 수동 생성은 상태 알림도 외부로 보내지 않는다.** 마지막으로 검증된 동일 채널이 여전히 활성 상태인 경우에만 허용하며 같은 발송·중복 규칙을 적용한다. 채널 자체 장애·인증 오류는 이 알림도 도착할 수 없으므로 웹의 다음 실행/마지막 결과에서 확인해야 한다. 별도 장애 알림 채널은 후속 범위다.

HTTP 5xx만으로 미접수라고 단정하지 않는다. 외부 메신저까지 포함한 완전한 1회 전달은 보장하지 않는다. 저장소 중복 실행 방지와 결과 불명 처리로 중복 위험을 줄인다. 수동 재발송은 중복 가능성을 보여 주고 명시적으로 실행한다.

디스코드 메시지는 2,000자 제한 안에서 **1,500자 목표의 단일 요약 + 전체 리포트 링크**로 만든다. 게시물의 `@everyone` 같은 문구가 알림을 만들지 않도록 `allowed_mentions.parse=[]`로 보낸다. 긴 원문·첨부파일은 MVP에서 발송하지 않는다.

## 9. 저장 정보와 접근 제어

| 자료 | 주요 필드 |
|---|---|
| 구독 | 제목·검색식·출처·요일/시각·기간·모델·수신 채널·켜짐·구성 버전 |
| 실행 | 구독 ID·예정 회차·기간·구성 스냅샷·단계·시도·실행권 만료·결과·오류 코드 |
| 리포트 | 생성된 본문·자료별 URL/발행일/확인 방식·생성 시각·불확실성 |
| 전달 | 리포트·채널·대상 구성 버전·대기/발송중/확인/실패/결과불명·외부 메시지 ID·시도 이력 |
| 알림 연결 | 종류·표시 이름·대상 확인 정보·연결 버전·검증 시각·비밀값 참조 |

리포트와 연결 설정은 인증 영역에 두고 외부 공유 토큰은 MVP에서 만들지 않는다. 메신저의 전체 보기 링크도 로그인 후 열린다. 공개 홈·포트폴리오에는 리포트를 노출하지 않는다.

연결 비밀값은 Mac 사용자만 읽을 수 있는 Git 제외 파일에 저장하고 파일 권한을 0600으로 제한한다. API 응답·브라우저 저장소·로그·리포트·일반 JSON 백업에 원문을 넣지 않는다. OS 키체인 연동은 필요성 확인 뒤 별도 범위로 다룬다.

출처 읽기는 사설·루프백·링크 로컬·메타데이터 주소를 차단하고 DNS 결과와 모든 리다이렉트 대상에 같은 제한을 적용한다. 알림 전송 주소는 정해진 플랫폼 HTTPS 호스트·경로로 제한하며 리다이렉트를 따르지 않는다. 사용자가 설정한 출처·키워드는 검색 제공자에, 리포트 내용은 선택한 메신저에 전달된다는 점을 설정 화면에 표시한다.

연결 대상을 교체하면 기존 검증을 무효화하고 해당 연결을 사용하는 예약을 꺼 둔다. 테스트 성공 후 사용자가 다시 켠다. 실행 중 수정된 예약·대상은 발송 직전에 구성 버전을 확인해 오래된 대상으로 보내지 않는다.

발송 전 예약·대상 버전이 다르면 해당 미발송 항목을 `설정 변경으로 취소`로 확정한다. 같은 회차를 자동 재생성·재발송하지 않는다. 이미 만든 리포트는 보관함에 남기고 새 설정의 즉시 실행은 사용자가 별도로 선택한다.

## 10. 검증과 완료 기준

| 시험 | 통과 조건 |
|---|---|
| 실제 수동 검색 | 원하는 주제로 발췌·원문 구분, 확인된 발행일·기간·중복 표시를 직접 확인 |
| 가짜 시계 시험 | 월요일·자정·재시작·48시간 경계·여러 주 누락에서도 회차와 기간이 일관됨 |
| 동시 실행 | 같은 회차를 두 번 탐지해도 실행·발송 대기 항목이 중복 생성되지 않음 |
| 장애 주입 | 검색·Ollama·DB 오류와 재시작에서 정상 0건과 실패가 섞이지 않음 |
| 애매한 발송 | 서버가 접수 후 연결을 끊는 시험에서 결과 불명이고 자동 중복 발송하지 않음 |
| 대상·예약 변경 | 대기 중 해제/수신처 교체 뒤 이전 대상으로 보내지 않음. 이미 전송된 건의 한계 표시 |
| 인증·비밀값 | 비로그인 접근·교차 출처 변경 차단, 출력·로그·백업에서 비밀값 미노출 |
| 출처 주소 공격 | 사설 주소, DNS·리다이렉트 우회, 과대 응답, 외부 본문의 명령을 차단·무시 |
| 개인 Mac 실검증 | 실제 검색 서비스·Ollama·승인한 채널 테스트와 로그인 세션의 월요일 예약 1회 성공 |
| 사용성 | 모바일에서 설정·미리보기·중지·실패 확인 가능. 웹 종료 후에도 Mac에서 실행 |

3단계의 코드 완료는 가짜 시계·장애 시험과 Mac의 가까운 시각 예약 시험으로 판정한다. **운영 검증 완료**는 이후 실제 월요일 1회 성공으로 별도 기록한다. 다음 월요일까지의 관찰 대기가 있을 수 있으며 구현 직후 운영 검증까지 끝났다고 표시하지 않는다. 자원 경합 3회·30분 만료, 실행권을 잃은 작업의 지연 복귀, 발송 직전 구성 변경도 필수 시험에 포함한다.

초기 운영 데이터는 실행 시간, 검색 성공/누락, 발송 확인/불명, 대화 지연만 최소 수집한다. 검색어와 비밀값을 상세 오류 로그에 덤프하지 않는다. 같은 채널의 상태 알림을 보조 수단으로 쓰되 채널 자체 장애의 별도 알림은 후속으로 결정한다.
